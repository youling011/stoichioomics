# Real Data Integration Guide

This platform is already structured so that the frontend consumes a stable **registry + species + omics artifact contract**, rather than talking directly to raw FASTA/GFF/feature-extraction code. To connect real data, keep that contract stable and replace the demo registry with a real registry.

## 1. What the running site reads

The backend `stoichdb` app reads a registry folder from `STOICHDB_DATA_ROOT`.

That folder must contain:

```text
<registry_root>/
  index.json
  <species_id>/
    cross_omics.json
    genome/
      rows.json
      summary.json
      analysis.json
    transcriptome/
      rows.json
      summary.json
      analysis.json
    proteome/
      rows.json
      summary.json
      analysis.json
```

The UI does **not** require that every artifact be produced by the website itself. In production, those files can be generated by external pipelines and then mounted into the backend.

## 2. Recommended production pipeline

Use a three-stage pipeline.

### Stage A. Feature extraction

Generate real stoichiometric feature tables from sequence-oriented sources.

Typical inputs:
- Genome: FASTA + GFF/GTF + optional promoter extraction rules
- Transcriptome: transcript FASTA / CDS / ORF-aware tables
- Proteome: protein FASTA or translated ORF products

Typical outputs:
- `genome_features.csv`
- `transcriptome_features.csv`
- `proteome_features.csv`

These should follow the project schemas you already defined, for example:
- genome: promoter/exon atoms per base, GC strata, codon bias, coordinates, strand
- transcriptome: nucleotide composition, atoms per nt, entropy, dinucleotide bias, ORF coupling
- proteome: element atoms per aa, ratios, pI, gravy, instability, aromaticity, disulfides

### Stage B. Artifact generation

Build species-level analysis artifacts from each feature table.

Required categories:
- `rows.json`: row-level entity table for browsing
- `summary.json`: distributions, feature cards, preview rows, scatter presets, coupling matrix, strategy breakdown
- `analysis.json`: outliers, trade-off front, omics-specific artifacts
- `cross_omics.json`: cross-omics join view, fingerprint, transformation summary

This is the correct place to run your real analysis modules:
- genome: promoter–exon shifts, stoichiometric islands, coupling edges, clusters, outliers
- transcriptome: RNA stoich-space typing, rare/outlier transcripts, RNA↔ORF coupling, motif themes
- proteome: resource budget spectra, element↔property coupling, Pareto fronts, outliers

### Stage C. Registry assembly

Combine all species into one registry folder and point the backend to that folder.

## 3. Fastest migration path from the current demo package

The package now includes a helper:

```bash
python scripts/build_stoichdb_from_real.py \
  --metadata data/real_input/species_metadata.csv \
  --input-root data/real_input/species_registry \
  --output-root data/real_registry
```

Then start the backend with:

```bash
STOICHDB_DATA_ROOT=/absolute/path/to/data/real_registry python manage.py runserver
```

The script supports a gradual migration path.

### Path 1. Minimal usable migration

Provide only row tables.

```text
data/real_input/species_registry/
  escherichia_coli_110957/
    genome/rows.csv
    transcriptome/rows.csv
    proteome/rows.csv
```

The script will automatically create fallback summary/analysis payloads so the site remains navigable.

### Path 2. Preferred migration

Provide row tables plus your real precomputed artifacts.

```text
data/real_input/species_registry/
  escherichia_coli_110957/
    cross_omics.json
    genome/
      rows.csv
      summary.json
      analysis.json
    transcriptome/
      rows.csv
      summary.json
      analysis.json
    proteome/
      rows.csv
      summary.json
      analysis.json
```

If `summary.json`, `analysis.json`, or `cross_omics.json` already exist, the script preserves them.

## 4. Metadata file requirements

Your metadata table must contain:
- `species_id`
- `display_name`
- `short_name`
- `domain`
- `clade`
- `habitat`
- `genome_size_mb`

Optional columns such as `genome_gc`, `promoter_gc`, `proteome_pi`, and `proteome_gravy` can also be included and will help seed the species fingerprint.

## 5. How to map your real schemas

### Genome

At minimum, provide a stable entity identifier, usually `gene_id`.

Strongly recommended fields:
- `gene_id`
- `gene_name`
- `start`, `end`, `strand`
- `exon_gc_percent`
- `promoter_gc_percent`
- `exon_atoms_N_per_base`
- `gc3_percent`
- `promoter_exon_gc_delta`
- `stoich_island_score`

### Transcriptome

At minimum, provide a stable transcript identifier.

Strongly recommended fields:
- `transcript_id`
- `gene_id`
- `gene_name`
- `gc_content`
- `nt_entropy`
- `atoms_per_nt_N`
- `atoms_per_nt_P`
- `orf_length_aa`
- `rna_orf_coupling_score`

### Proteome

At minimum, provide a stable protein identifier and a cross-omics join key.

Strongly recommended fields:
- `protein_id`
- `ensembl_gene_id` or `gene_id`
- `gene_name`
- `N_atoms_per_aa`
- `S_atoms_per_aa`
- `pI`
- `gravy`
- `resource_budget_score`
- `disulfide_density`

## 6. Cross-omics join rule

Production integration should preserve one canonical join key across omics.

Recommended rule:
- `genome.gene_id = transcriptome.gene_id = proteome.ensembl_gene_id`

If your proteome table uses a different field name, normalize it during artifact generation.

## 7. How user-uploaded data fits in

The public registry and user-upload workflows should remain separate.

Recommended split:
- `stoichdb`: curated public or internal registry for browsing and comparison
- `jobs` / `hvg`: user-owned uploads and on-demand computation

For custom user data, use sequence-oriented uploads to produce temporary feature tables and artifacts under job-specific workspaces. Once validated, those same artifacts can be promoted into the long-term registry.

## 8. Scaling to ~30,000 species

For a production-sized registry:
- keep `rows.json` per species/omics partitioned by species
- precompute `summary.json`, `analysis.json`, and `cross_omics.json`
- avoid generating heavy analysis on the fly in request handlers
- generate `index.json` as a compact searchable registry manifest
- keep fingerprints small and fixed-width for fast compare pages
- add background ETL / artifact refresh jobs rather than computing in the request path

## 9. Practical recommendation

The best route is:
1. keep your existing genome/transcriptome/proteome feature extractors as the source of truth
2. add artifact-builder scripts that emit the JSON contracts expected by this site
3. assemble those outputs into a registry folder
4. switch `STOICHDB_DATA_ROOT` from the demo folder to the real registry folder

That lets you upgrade the platform from demo mode to real data mode without changing the frontend information architecture.
